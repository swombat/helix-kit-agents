# Secrets — the model

This repo handles two distinct categories of secret. Keeping them separate is the design.

## 1. The bearer tokens (HelixKit ↔ agent communication)

Generated by HelixKit during the promote wizard. Two of them:

- **Outbound `hx_` token** — used by the agent when calling HelixKit's REST API with curl. Messages posted with it are attributed to the agent.
- **Inbound `tr_` token** — used by HelixKit when calling the agent's `/trigger` endpoint.

These never touch you in plaintext during normal operation. HelixKit encrypts them with a master key (also generated during the wizard) and commits the encrypted blob (`credentials.yml.enc`) to the per-agent repo. The wizard shows you the master key once.

The encrypted credentials also contain the agent repo's GitHub deploy key. `bin/generate-env` writes it to `.agent-deploy-key` during deploy and the container mounts it at `/run/agent-deploy-key` for git push access.

You commit the encrypted blob. You safeguard the master key.

## 2. The LLM provider key (agent ↔ Anthropic/OpenAI/etc.)

This is YOUR key, from your provider account. The bill comes to you. It never enters the repo.

Set it as a file on the deploy host:

```bash
# On the deploy host, as the user that will run docker compose:
sudo install -d -m 700 -o $USER /etc/helix-kit-agents/wing
install -m 600 /dev/null /etc/helix-kit-agents/wing/.host-env
cat > /etc/helix-kit-agents/wing/.host-env <<EOF
ANTHROPIC_API_KEY=sk-ant-api03-...
EOF
```

`bin/generate-env` reads this file (via `set -a; . .host-env; set +a`) and merges its contents into the `.env` it produces for docker compose.

## The master key

The master key is **32 random bytes, base64-encoded** — about 44 characters. HelixKit generated it once and showed it to you in the promote wizard.

If you lose it, the encrypted credentials become useless. There is no recovery — you have to re-run the wizard, which generates a fresh master key and a fresh encrypted blob.

**Where to store it:**

- Your password manager (1Password, Bitwarden, etc.) under an entry named `<agent_id>-master-key`
- On the deploy host at `/etc/helix-kit-agents/<agent_id>/master.key` (mode 0600)

**Rotation:** if you suspect the master key has leaked:

1. Run the "Rotate credentials" action in HelixKit's agent settings (generates fresh master key + encrypted blob)
2. Replace `credentials.yml.enc` in your repo
3. Replace `/etc/helix-kit-agents/<agent_id>/master.key` on the deploy host
4. Run `bin/deploy` (which re-decrypts and restarts)

The bearer tokens themselves haven't changed — only the encryption around them. To rotate the bearer tokens, see the "Rotate trigger token" action in HelixKit, which is independent.

## Encryption details (for the curious)

`credentials.yml.enc` is a YAML wrapper around AES-256-GCM ciphertext:

```yaml
algorithm: aes-256-gcm
nonce: <base64 12-byte nonce>
ciphertext: <base64 (ciphertext + 16-byte AES-GCM auth tag)>
helix_kit_signature: <hex sha256-hmac of plaintext, optional>
```

The plaintext, before encryption, is a YAML mapping like:

```yaml
agent_id: wing
agent_uuid: 7a2c89e5-...
helix_kit:
  app_url: https://helix-kit.example.com/
  bearer_token: hx_...
trigger:
  bearer_token: tr_...
github:
  deploy_key: |
    -----BEGIN OPENSSH PRIVATE KEY-----
    ...
```

Decryption (Python, what `bin/generate-env` does):

```python
from cryptography.hazmat.primitives.ciphers.aead import AESGCM
import base64, yaml
key = base64.b64decode(open(master_key_file).read().strip())
blob = yaml.safe_load(open("credentials.yml.enc"))
nonce = base64.b64decode(blob["nonce"])
ct_and_tag = base64.b64decode(blob["ciphertext"])
plaintext = AESGCM(key).decrypt(nonce, ct_and_tag, None)
creds = yaml.safe_load(plaintext)
```

`helix_kit.app_url` is the Rails app URL used for REST calls such as announce and agent post-backs.
External agents use `helix_kit.app_url` plus `helix_kit.bearer_token` to call HelixKit's REST API with curl.

Encryption (Ruby, what HelixKit does):

```ruby
require "openssl"; require "base64"
cipher = OpenSSL::Cipher.new("aes-256-gcm").encrypt
cipher.key = master_key  # 32 random bytes
nonce = SecureRandom.bytes(12)
cipher.iv = nonce
ciphertext = cipher.update(plaintext) + cipher.final
tag = cipher.auth_tag
# Then YAML-wrap with base64-encoded nonce + (ciphertext + tag)
```

This deliberately doesn't use Rails' `ActiveSupport::EncryptedFile` format because that requires Ruby on the deploy host. Plain AES-256-GCM is implementable in any language with a few lines.

## Why not commit the master key alongside the encrypted blob?

Then it wouldn't be encryption.

## Why not just gitignore the plaintext credentials?

Then `git push --force` (or a misconfigured CI, or a momentary `git add .` from another directory) can leak them. The encrypted file is safe to be sloppy with; the plaintext file requires the user to never make a mistake.

## Manual setup (no HelixKit wizard)

If you're bringing up an agent manually, you'll need to:

1. Generate a master key:
   ```bash
   openssl rand -base64 32 > master.key
   ```
2. Author the plaintext credentials YAML (with bearer tokens you've obtained from HelixKit's API)
3. Encrypt it. Easiest way: write a 30-line Ruby/Python script that takes the master key and the plaintext YAML, produces the encrypted YAML wrapper. The format spec is above.

This path is for advanced setups. Most users go through the HelixKit promote wizard, which does steps 1-3 for you.
